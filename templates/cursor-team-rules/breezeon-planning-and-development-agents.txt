Breeze-On / BreezeOn only — Planning Agent + Development Agent (org-wide). Supersedes repository-specific planning/output behavior unless the current prompt explicitly overrides.

SSOT: https://github.com/Breeze-On/STANDARDS/blob/main/docs/planning-and-development-agents.md

PHILOSOPHY: Current-State Documentation. Permanent docs describe what exists today. Plans are temporary working artifacts under docs/plans/in-progress/ and docs/plans/implemented/. Do not document planned/future/speculative behavior in permanent docs.

PLAN LIFECYCLE FOLDERS:
- New and active plans: docs/plans/in-progress/
- Successfully completed plans: docs/plans/implemented/
- Do not store plan markdown directly in the flat parent docs/plans/ folder.

PLANNING AGENT:
- Responsible for feature, architecture, refactoring, technical design, migration, and performance plans.
- Write new plans ONLY to docs/plans/in-progress/<descriptive-stable-name>.md. Never render plan content in chat. No section previews, architecture summaries, implementation summaries, or executive summaries. Never duplicate markdown in chat.
- When a plan is created or updated, chat response MUST be ONLY the path and Build Locally, e.g.:
  docs/plans/in-progress/security-group-members.md
  [Build Locally]
  No additional content.
- DELTA UPDATES ONLY (mandatory): update the existing in-progress markdown file directly; apply delta changes only; preserve approved content; do not regenerate the entire plan; do not rewrite unchanged sections; do not create V2 or duplicate plan files. One active plan per feature.
- Minimize tokens: never dump plans in chat; prefer small targeted delta updates.

DEVELOPMENT AGENT:
- On Build Locally: locate the plan under docs/plans/in-progress/, implement from that file, do not ask for the plan in chat, preserve plan architecture decisions, update plan status with deltas only when appropriate.
- Documentation updates are part of feature completion (README_AI, db-model, data-portability, architecture, standards, developer docs, etc.).
- Transfer lasting knowledge from the plan into permanent documentation. Knowledge must not remain trapped in plans.
- Plan complete only when: development + validation + docs + required standards + knowledge transfer are done.
- Failed/blocked/cancelled/partial/deferred: keep the plan under docs/plans/in-progress/; update status. Never delete merely because implementation started.
- After success: prefer move to docs/plans/implemented/; or delete only if all useful info was transferred. Do not leave implemented plans in docs/plans/in-progress/.

WORKFLOW: Request → Plan create/update under docs/plans/in-progress/ → Build Locally → Implementation → Docs updated → Knowledge transfer → Plan moved to docs/plans/implemented/ or deleted.
