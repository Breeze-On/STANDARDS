# ADR-024 — Platform Process Root (two-tier Process model)

## Status

Accepted

## Context

Prior STANDARDS treated each product application's `{UniqueCode}.Process` table as the **sole runtime process root**. That model cannot support cross-application platform capabilities (workflow runtime, attachments, comments, notifications, shared history) that must relate to a process without knowing application-specific keys.

This decision migrates the platform from a **single-tier** Process model to a **two-tier** Process model. That migration is the **primary architectural decision** of the Process Platform Capabilities initiative.

## Decision

### OLD MODEL → NEW MODEL

| | OLD MODEL | NEW MODEL |
| --- | --- | --- |
| Platform / runtime root | `{UniqueCode}.Process` = runtime process root | **`Global.Process`** = platform runtime process root |
| Application table | Same table held identity + all business fields | **`{UniqueCode}.Process`** = application-specific process **extension** |

### Ownership

| Asset | Owner |
| --- | --- |
| Schema `Global` | breezeon-system-admin-eac |
| Table `Global.Process` | breezeon-system-admin-eac |
| Create procedure `Global.P_POST_Process` | breezeon-system-admin-eac |
| `{UniqueCode}.Process` (extension) | Product application repository |

### `Global.Process` contract (intentionally minimal)

| Column | Role |
| --- | --- |
| `ProcessId` | Internal IDENTITY primary key only |
| `ApplicationEnabledGUID` | Application Context binding |
| `ProcessGUID` | Universal platform process identifier (SQL-generated; consumers use this) |
| Audit quartet | Mandatory transactional audit columns |

No workflow, lifecycle, or status columns. No future-state assumptions in the table shape.

### ProcessGUID

- Generated by SQL on `Global.Process` (`DEFAULT NEWSEQUENTIALID()`).
- **Application repositories must not mint `ProcessGUID` values.**
- Consumers (URLs, FKs, future platform features) use `ProcessGUID` only.
- `ProcessId` on either table is an internal implementation key only.

### Authoritative create path

Products **must not** `INSERT` into `Global.Process` directly. Orchestration calls **`Global.P_POST_Process`** only.

### Mandatory persistence order

1. Create `Global.Process` via `Global.P_POST_Process`.
2. Database generates `ProcessGUID`.
3. Create application-specific `{UniqueCode}.Process` row using that `ProcessGUID`.
4. Commit transaction.
5. Return `ProcessGUID`.
6. Redirect to Process View.

Partial persistence must not occur (single shared-database transaction).

### Application Enabled deletion (fail-closed)

`Global.Process` rows are **runtime records**. Application Enabled deletion **must fail** when dependent `Global.Process` rows exist. The platform must **never** silently cascade-delete runtime process records. (Extends [ADR-006](ADR-006-application-context-ownership.md).)

### Process View (v1)

Route: `/process-view?AE={ApplicationEnabledGUID}&PGUID={ProcessGUID}`.

- Owned as a platform capability / shared pattern by breezeon-system-shared-ui (implementation shape proposed at implement time).
- All fields read-only display (not Disabled).
- No page footer / sticky actions.
- **Terminal in v1:** Create → Save/Submit → Process View. Out of scope: Edit, Resume, Reopen, Withdraw, Delete, return to editable state.
- Validation failures use the existing Application Error framework — no custom Process error screens.

### Save / Submit

Same persistence path. Submit enforces mandatory validation; Save does not. No workflow execution, process state, or lifecycle tracking in this decision's scope.

### Distinct from Process Framework

[ADR-019](ADR-019-process-framework-metadata.md) remains: Process Framework tables under `System` hold **definition** metadata only. `Global.Process` is the **runtime** platform root — orthogonal to PF metadata.

## Consequences

- `docs/database.md` Process table convention is rewritten to the two-tier model.
- Product apps keep `{UniqueCode}.Process` for business fields but consume platform `ProcessGUID`.
- AE delete SP must fail closed when `Global.Process` dependents exist.
- EAC Framework Synchronization allowlist includes `Global` schema objects.
- Consumer DE persistence wording remains Codes on `{UniqueCode}.Process`; platform identity is `ProcessGUID` from `Global.Process`.
